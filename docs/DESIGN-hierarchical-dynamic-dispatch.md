## 0. 요약 (TL;DR)

현재 실행 코어는 **중앙 결정적 레포락 스케줄러 + per-user 워커**로 구성되고, 실제 코딩은
각 워커 안에서 **일회성(one-shot) `claude -p`** 오케스트레이터가 수행한다. 이 one-shot
모델이 **HAN-537 계열 실패**의 근본 원인이다: 워커 안의 오케스트레이터가 코드 편집을
백그라운드 서브에이전트에 위임하고 "완료 알림을 기다리겠다"며 턴을 종료하면, one-shot
프로세스에는 **다음 턴도 알림 전달 경로도 없어** 커밋 없이 종료한다 → FAILED, 편집물은
미커밋으로 남고 공유 워크스페이스만 오염된다.

제안하는 목표 아키텍처는 **계층형·온디맨드·지속하지만 임시(persistent-but-ephemeral)인
위임 트리**다. 각 노드는 살아있는(await 가능한) 세션으로 떠서 "위임하고 응답을 기다린다"가
턴을 넘어 성립하고, 배정된 티켓이 모두 소진되면 **종료**한다(상시 데몬 아님). 레포락은
결정적 상호배제 **메커니즘**으로 남기고, "무엇을/언제/얼마나"의 **정책**만 에이전트 판단으로
옮긴다. 잡 수 상한 대신 **컨테이너 단위 도커 자원 한도**가 결정적 안전 경계가 된다.

**범위 경계 (불가침)**: 이 재설계는 **전부 `jira-auto-dispatcher`(하네스) 레이어에서만**
구현한다. `ai-dlc-orchestrator` 프레임워크(룰북·에이전트 정의·스펙)는 **불가침이며 한 줄도
바꾸지 않는다**. HAN-537조차 룰북 수정이 아니라 하네스의 실행 모드 변경(one-shot → 지속
세션)만으로 닫힌다(§3.0, §3.0.1).

**중요 — 코드는 이미 이 문서 초판의 as-is보다 크게 진행돼 있다.** 아래 §1은 실제 현행
코드를 정확히 기술한다. 목표(§2)의 상당 부분이 **이미 착지**했다:
- **지속 세션(Phase 1b) 착지** — one-shot `claude -p`는 **기본값이 지속 세션**(양방향
  `--input-format/--output-format stream-json`)으로 바뀌었다(`agent_runner.py:511-602`,
  stdin 주입 `:605-616`, 세션 수명/유휴 워치독 `:891-`). **HAN-537의 근본 원인은 닫혔다**
  (§2.1은 이제 과거형). 단, 현재는 **워커 계층에서 티켓 1건당 한 세션**으로만 쓴다 —
  이 "살아있는 세션에 후속 메시지 주입" 메커니즘을 **중앙 Tier-1/2로 확장**하는 것이 §4 Phase 3b.
- **dlc-meta 센트럴 단일 라이터(Phase 3a, MR !21) 착지** — `app/dlc_meta_writer.py`.
  완료(terminal) 회신 시 사이클로그를 master에 커밋·push하고 `cycle_log_path`를 회신에
  실어준다(`dispatch.py:118-129`). **사이클 컨텍스트가 위로 흐르는 핸드오프 경로**다.
- **freshen-on-dispatch(MR !22) 착지** — `app/freshen.py`. `scheduler.tick`이 실제
  dispatch할 때만 미락 참고 레포를 기계적으로 최신화한다(`scheduler.py:204-215` on_dispatch 훅).
- **자원 기반 어드미션·per-user 병렬·셀프 토큰 스로틀·핸드오프·Jira 웹훅**도 이미 착지(§1.6).
- **센트럴은 이미 ai-dlc-orchestrator 에이전트를 돌린다** — cwd `…/workspace/orchestrator`
  의 `claude`가 오케스트레이터 정체성으로 응답한다. **단, 그 에이전트의 현재 용처는
  `app/repo_resolver.py`(신규 티켓당 대상 레포 판단) 하나뿐**이다. 스케줄링/디스패치는 전부
  **결정적 파이썬**(`RepoLockScheduler` + 자원 어드미션)이 한다(§1.2·§1.7).

남은 핵심 격차는 (a) **센트럴 에이전트를 repo-resolver-only → 조율 허브(Tier-1/2)로 확장**
(§4 Phase 3b), (b) 단방향 채널 F → **티켓 correlate 요청/응답(await)** 트랜스포트,
(c) 병렬 단위 워크트리 격리(Phase 2)다.

## 1. 현행 아키텍처 (As-Is, 실제 코드 기준)

### 1.1 2-역할 구조 — central 과 worker

- **central**: 폴러/웹훅 → dedup 게이트 → 사용자·레포 해석 → 스케줄러 enqueue → per-user
  워커 컨테이너 spawn → HTTP 디스패치 허브. 코드를 편집하지 않는다.
- **worker**: per-user 컨테이너. 사용자 본인의 Jira/GitLab 토큰·git author로 실제 코딩을
  수행하는 `claude` 오케스트레이터를 돌린다.

### 1.2 스케줄러 — `app/scheduler.py` (`RepoLockScheduler`)

- **레포 단위 락 = 활성 잡 상태의 순수 함수.** 별도 락 테이블을 영속하지 않고 매 tick마다
  `jobs.json`에서 재계산 → 재시작 후 자동 복원 (`_snapshot()` `scheduler.py:469-494`).
  한 레포에 활성(running/cancelling/handing_off) 잡은 1개, 서로 다른 레포는 병렬
  (`_pick_eligible()` `scheduler.py:509-526`).
- **⚠️ 잡 수 cap은 이미 제거됨.** 태스크가 언급한 `global_concurrency=3` /
  `concurrency_per_worker=1` 는 **더 이상 코드에 없다**(커밋 `c6eabca`가 고정 cap →
  자원 기반 어드미션으로 전환). 현재 스로틀은 **서버 자원**뿐이다:
  - 메모리 헤드룸(PRIMARY): `effective_mb = mem_available - running_count *
    per_job_mem_reserve_mb`, `< min_free_mem_mb`면 큐잉 (`scheduler.py:183-189`).
  - 부하 상한(2차): `loadavg_1min / ncpu >= max_load_per_core`면 큐잉
    (`scheduler.py:177-182`). 기본값 `min_free_mem_mb=1536`, `per_job_mem_reserve_mb=1024`,
    `max_load_per_core=0.9` (`scheduler.py:143-145`).
  - 프로브는 호스트 `/proc/meminfo`·`/proc/loadavg`(컨테이너 안에서도 호스트 값 보고)를
    읽고, 못 읽으면 **fail-open**(무압박 admit) — 정확성은 레포락이 보장
    (`default_resource_probe()` `scheduler.py:80-95`).
- **미해석(`target_repos=[]`) = 전역 직렬**: REPO-MAP으로 레포를 못 정한 잡은 단독 실행
  (`global_lock`, `scheduler.py:481-484`, `_pick_eligible` `scheduler.py:518-521`).
- tick / on_complete / on_interrupt / report 로 상태 전이 (`scheduler.py:156-261`). terminal
  보고 시 상태를 바꾸면 레포락이 함수적으로 자동 해제 → 다음 tick에서 대기 잡 dispatch.
- **재개**: `interrupted + reset_at` 잡은 reset_at 도래 전까지 적격 풀에서 제외
  (`_eligible_now` `scheduler.py:496-507`).

### 1.3 워커 — `app/worker.py` (`worker_loop`) — **은퇴·삭제됨**

- per-user 워커가 `GET /dispatch/<user>/next`로 잡을 수령, `run_job`으로 실행, 회신.
- **⚠️ per-user 병렬은 이미 착지**(커밋 `f9eef29`, "Increment 2"). `worker_loop`는
  `concurrency>1`이면 `_run_concurrent_loop`로 분기 — **스레드 풀**로 서로 다른(레포가
  다른, central 레포락이 보장) 잡을 동시 실행 (`worker.py:1039-1048`, `_run_concurrent_loop`
  `worker.py:863~`). `concurrency=1`이면 기존 단일 잡 경로와 100% 동치(회귀 안전,
  `worker.py:1050-1086`).
- `worker_max_concurrency` 기본 **64**는 정책 cap이 아니라 runaway 방지 **안전 상한**
  (`worker.py:32`, `_worker_concurrency` `worker.py:154-`). 진짜 스로틀은 central의 자원
  어드미션.
- `GET /next`는 `?exclude=T1,T2`로 워커가 이미 처리 중인 티켓을 배제하고 **다른** running
  잡을 반환 → 워커가 서로 다른 잡을 동시에 수령 (`dispatch.py:151-173`,
  `next_for_user` `scheduler.py:447-463`).
- **⚠️ 워크스페이스는 여전히 단일 공유 클론.** 잡의 cwd는 `os.path.join(workspace, repo)`
  로 **레포별 한 디렉토리**를 공유한다 (`worker.py:478-484`, `565-572`). git worktree
  격리는 **없다** — 병렬은 "서로 다른 레포"라 디렉토리가 갈려서 성립할 뿐, **같은 레포의
  병렬 잡은 레포락이 직렬화**한다. 같은 레포에서 워크트리로 병렬화하는 경로는 미구현.

### 1.4 에이전트 러너 — `app/agent_runner.py` (**Phase 1b 지속 세션 착지 — HAN-537 지혈 완료**)

- **⚠️ 초판의 "one-shot `claude -p`"는 STALE.** 실행 모드는 **기본값이 지속 세션**으로
  전환됐다(`persistent_enabled` 기본 True, `build_command` `agent_runner.py:547-602`):
  ```text
  claude -p --input-format stream-json --output-format stream-json --verbose \
         --dangerously-skip-permissions \
         --session-id <uuid5(ticket)>          # 신규 (재개: --resume <sid> [--from-pr N])
  # 프롬프트는 인자가 아니라 stdin에 user 메시지 JSON 라인으로 주입
  ```
  - **stdin 주입**: `_encode_user_message` `agent_runner.py:605-616` — `{"type":"user",
    "message":{...}}` 한 줄을 살아있는 세션 stdin에 append하면 새 턴(사용자 후속 지시)으로
    처리된다. `_write_stdin`/`_close_stdin` `:848-867`.
  - **세션 수명 워치독**: 최대 벽시계(`DEFAULT_SESSION_MAX_SEC=7200`)·유휴 상한
    (`DEFAULT_SESSION_IDLE_SEC=1800`) 초과 시 stdin EOF로 정상 종료
    (`_start_session_watchdog` `agent_runner.py:891-`). **지속하되 영구는 아님**(§3.2-3).
  - **레거시 one-shot 폴백 경로 유지**: `run.persistent_session=False` 또는 스트림 포맷이
    아니면 옛 `claude -p "<prompt>"` 로 안전 롤백(`build_command` else 분기 `:584-592`).
  - session-id = 티켓 기반 결정적 uuid5 = 재개 키(`deterministic_session_id`
    `agent_runner.py:423-425`, 신규 `:600` / 재개 `:594-598`).
- 결과 판정(`_consume`): `rc==0 and not error_seen` → DONE, 한도 감지 → INTERRUPTED,
  그 외 → **FAILED**. **완료 판정 불변식**: pending 백그라운드 태스크가 0인 상태의 `result`
  이벤트가 진짜 완료 → 그때 stdin을 닫는다(`agent_runner.py:39-43` 주석).
- **함의(§2.1 근본 해결)**: 세션이 살아있으므로 오케스트레이터가 편집을 백그라운드
  서브에이전트에 위임하고 턴을 종료해도 **완료 알림이 다음 턴으로 배달**돼 이어서 커밋한다.
  이것이 one-shot이 못 하던 것 = HAN-537의 근본 해결(Phase 1b, §2.1은 이제 **과거형**).
- **⚠️ 아직 안 쓰는 잠재력**: 이 "여러 티켓을 한 세션에 순차 주입하며 각각 await" 메커니즘은
  현재 **워커에서 티켓 1건당 한 세션**으로만 쓴다. Phase 3b는 **바로 이 메커니즘을 중앙
  Tier-1/2 노드에 재사용**해 한 노드가 여러 티켓을 배치로 흡수·조율하게 한다(§4).

### 1.5 폴러·큐·게이트·스포너

- **폴러** `app/poller.py`: (A) 신규-티켓 ∪ (B) 담당자-enabled-변경 → `gate.claim(ticket)`
  → `resolve_user` → `target_repos` 해석(LLM: dlc-meta REPO-MAP, 실패 시 정적 폴백) →
  `dispatcher.enqueue` (`poll_once` `poller.py:475-580`).
- **dedup 게이트** `app/gate.py`: 티켓 키 원자적 claim, 최초 1회만 True, state.py로 영속
  (`gate.py:36-46`). 폴러·웹훅 공통 수렴점.
- **큐** `app/queue.py`: `Job(user, target_repos, status, …)`. 상태 집합 —
  `ACTIVE_STATUSES={running, cancelling, handing_off}`,
  `TERMINAL_STATUSES={done, failed, cancelled, handed_off}` (`queue.py:54-71`). JobQueue는
  state.py로 영속 (`queue.py:162-265`).
- **스포너** `app/spawner.py`: 단일 이미지로 `jad-worker-<username>` 컨테이너 spawn.
  **컨테이너 단위 자원 한도가 이미 존재**: `mem_limit`(예: `4g`) (`spawner.py:31`),
  per-user 시크릿 파일 ro 마운트, GitHub 토큰 제거(central 전용). ⚠️ docker.sock 특권 →
  socket-proxy 권고 (`spawner.py:41-47`).
- **채널 F 상태 콜백(여전히 단방향)**: 워커 → `POST /dispatch/<user>/<job>/status`
  {status, log_summary, reset_at, branch, session_id, mr_url, audit_refs, rolledback}
  (진행중/done/failed/interrupted/cancelled/handed_off). central은 이 **단방향 비동기**
  회신을 스케줄러 상태머신에 반영(`report_status` `dispatch.py:92-129`). 워커는
  `GET /next`(폴), `GET …/control`(취소/핸드오프 폴)로만 반대 방향을 읽는다 →
  **티켓 단위로 blocking-await할 요청/응답이 아직 없다**(Phase 3b enabler 5의 표적).
- **⚠️ dlc-meta 단일 라이터 회신 편승(Phase 3a 착지)**: 완료(terminal ∈ {done, failed,
  handed_off}) 회신이면 `report_status`가 `dlc_meta_writer.commit_cycle_log(job)`을 호출해
  사이클로그를 master에 커밋·push하고, 커밋 상대경로를 `result["cycle_log_path"]`로 실어
  회신한다(`dispatch.py:118-129`). **사이클 컨텍스트가 위로 흐르는 통로** — Phase 3b의
  Tier-2 "리뷰"는 이 경로를 읽는다.

- **축1 셀프 토큰 쿨다운**: 이 호출이 429/usage-limit 신호를 보이면 `CentralAIRateLimited`로

  → **조율 허브(Tier-1)**.

## 2. 문제 정의 (Grounded)

### 2.1 HAN-537 계열 실패 — one-shot 오케스트레이터의 구조적 결함 (✅ **Phase 1b로 해결됨**)

> **상태 갱신**: 이 절이 진단한 근본 원인은 **Phase 1b(지속 세션)로 닫혔다**(§1.4). 아래는
> **왜 그 픽스가 옳았는지**를 남기는 근거 기록(과거형)이다 — 미해결 문제가 아니다.

**근본 원인은 하네스(디스패처)에 있고 프레임워크 룰북에 있지 않다.** 룰북의 "백그라운드
위임 후 완료 알림 대기"는 정상 동작이며(HAN-534도 같은 룰북으로 성공), 실패를 만든 것은
하네스가 그 오케스트레이터를 **단발 `claude -p`로 띄웠던 실행 모드**다. 상세 논거는 §3.0.1.

워커 안의 오케스트레이터는 headless one-shot `claude -p`다(§1.4). 그 오케스트레이터가
코드 편집을 **백그라운드 서브에이전트**에 위임하고 **턴을 종료**하며 "백그라운드 작업이
끝날 때까지 대기합니다"라고 말하면:

- one-shot 프로세스에는 **다음 턴이 없다** — 완료 알림을 받아 이어서 커밋할 실행 문맥이
  존재하지 않는다. 스트림이 끝나면 프로세스가 종료된다.
- 결과: 커밋 없이 종료 → `rc`/이벤트 기준 **FAILED**(`agent_runner.py:768-775`),
  서브에이전트 편집물은 **미커밋**으로 남고, `auto/HAN-537` 브랜치는 **커밋 0개인데
  워킹트리는 dirty**.
- **결정적**으로 재현되며, 재실행할 때마다 **공유 워크스페이스를 재오염**한다(§1.3의 단일
  공유 클론).

**증거**: 세션 트랜스크립트 마지막 레코드 = assistant `end_turn` "백그라운드 작업이 끝날
때까지 대기합니다"; `auto/HAN-537` 브랜치 커밋 0 + 워킹트리 dirty.

**대조(성공)**: HAN-534는 구현 서브에이전트를 **포그라운드**(`run_in_background=False`)로
띄워 **같은 턴 안에서** 결과를 받아 커밋 → 정상 완료. 즉 실패/성공을 가른 것은 위임
자체가 아니라 **"턴을 넘겨 await"가 one-shot에서 불가능**하다는 점이다.

### 2.2 사용자 내부(within-user) 직렬화 — 부분 해소, 잔여 있음

- 과거 `concurrency_per_worker=1`는 제거됐고 per-user 병렬이 착지했다(§1.6). 그러나
  병렬은 **서로 다른 레포**일 때만 성립한다(디렉토리가 갈림).
- **잔여 문제**: 같은 사용자가 **같은 레포**의 여러 티켓을 가지면 레포락이 직렬화한다.
  워크트리 격리가 없어(§1.3) 같은 레포 병렬을 안전하게 열 수 없기 때문이다. 서로 다른
  워크트리라면 병렬 가능한 작업도 현재는 직렬로 남는다.

### 2.3 자원 경계 — 대체로 해결, 루프가드 재설계 필요

- 고정 `global=3`/`per_user=1` 상한은 이미 자원 인지 어드미션으로 대체됐다(§1.6).
- ⚠️ 단, 태스크가 지적한 대로 옛 `per_user_cap=1`은 **재귀-디스패치 루프 방지** 역할도
  겸했었다. 현행 코드에서 그 역할은 이미 **dedup 게이트(티켓 키) + 상태 전이 워터마크**가
  대신한다(`poller.py:480-481`, `542-548`, `582-589`). 하지만 **시스템이 티켓을 생성**할 수
  있는 계층(목표 §3)에서는 이것만으로 부족하다 — **provenance/depth 기반 루프가드**가
  추가로 필요하다(§3 enabler 3).

### 3.0 Non-goals / 불변식 (Invariants) — 소유 경계

이 재설계의 **범위와 경계**를 먼저 못 박는다. 아래는 협상 대상이 아니다.

**불변식 (반드시 유지):**

1. **`ai-dlc-orchestrator` 프레임워크는 불가침(inviolable)이다.** 이번 재설계는 **전부
   `jira-auto-dispatcher`(하네스) 레이어에서만** 구현한다. 오케스트레이터 룰북·에이전트
   정의·스펙(`agents/*.md`, `agents/orchestrator/*`, `specs/*`, `templates/*`)은 **한 줄도
   건드리지 않는다.**
2. **Tier-3(사용자 컨테이너 오케스트레이터)와 Tier-4(레포 ai-dlc 서브에이전트)의 동작은
   프레임워크가 지금 하는 그대로다.** 디스패처는 그것들을 **어떻게 띄우고(실행 모드), 얼마나
   오래 살리고(세션 수명), 어떻게 말을 거는지(전송로)** 만 바꾼다.
3. **per-user attribution 불변**: 실제 작업은 각 사용자 본인 컨테이너에서 그 사용자의
   Jira/GitLab 토큰 + git author로 돈다(enabler 4). Central은 사용자 자격을 만지지 않는다.
4. **레포락은 결정적 상호배제 메커니즘으로 유지**(enabler 2) — 제거·약화하지 않는다.
5. **재시작 안전성 유지**: 락/큐/dedup은 상태의 함수로 복원 가능해야 한다(현행 `jobs.json`/
   `state.py` 불변식).

**Non-goals (이번 범위 아님):**

- 오케스트레이터/ai-dlc 룰북의 프롬프트·행동 규율 변경. (HAN-537은 룰북을 고쳐서가 아니라
  하네스 실행 모드를 고쳐서 닫는다 — §3.0.1.)
- ai-dlc 서브에이전트(Tier-4) 내부 로직·프롬프트 변경.
- 레포별 CI/CD, 코드리뷰 정책, Jira 워크플로우 자체의 변경.
- 크로스-오거니제이션/멀티테넌시 일반화(현재는 사내망·팀 단위 전제).

#### 3.0.1 왜 프레임워크를 안 바꾸고도 HAN-537이 닫히나 (핵심 논거)

HAN-537의 근본 원인은 **룰북 behavior가 아니다.** 오케스트레이터 룰북이 "코드 편집을
백그라운드 서브에이전트에 위임하고 완료 알림을 기다린다"고 지시하는 것은 **정상적이고
바람직한** 동작이다 — 성공한 HAN-534도 같은 룰북을 따랐다. 실패를 만든 것은 **하네스가 그
오케스트레이터를 단발 `claude -p`로 띄웠다**는 실행 모드다(`app/agent_runner.py:481-522`).
one-shot 프로세스에는 다음 턴이 없어, 백그라운드 완료 알림이 배달될 살아있는 실행 문맥이
없기 때문에 룰북이 의도한 "대기 후 재개→커밋"이 **물리적으로 불가능**했다.

따라서 하네스가 **실행 모드만** 지속 세션(`claude --input-format stream-json`, 또는 Agent
SDK 세션)으로 바꾸면, **바로 그 동일한 룰북 동작이 정상 작동한다**: 세션이 살아있으므로
백그라운드 서브 완료 알림이 다음 턴으로 도착 → 오케스트레이터 재개 → 커밋. 즉
**프레임워크(agents/*.md, specs/*)를 한 줄도 안 바꾸고**, 디스패처의 invocation 변경만으로
HAN-537이 닫힌다. 이것이 Phase 1의 핵심 논거다(§4).

### 3.1 4-티어 위임 트리 (소유 경계 표시)

```text
╔══════════════════════ 디스패처(하네스) 소유 — 이번 재설계 범위 ══════════════════════╗
║ Tier 1  중앙 오케스트레이터 에이전트  (일이 있는 동안만 지속, 스케줄링/조율 전담, 코드 편집 X) ║
║           │  레포락 상태 + 실시간 자원 헤드룸을 읽어 어느/몇 개/어떤 순서를 동적 결정         ║
║           ▼                                                                              ║
║ Tier 2  중앙 서브에이전트  (사용자별 또는 태스크별)                                        ║
║           │  티켓 배치 → 순서·병렬성 자가 판단 → 아래로 위임 → 응답 await → 리뷰 → 위로 보고 ║
╚══════════════════════════════════════════════════════════════════════════════════════╝
            │  ── 소유 경계선: 여기부터 아래는 ai-dlc-orchestrator 프레임워크가 "그대로" 하는 일 ──
            ▼
┌────────────────────── 프레임워크(ai-dlc-orchestrator) 소유 — 불가침, 미변경 ──────────────────────┐
│ Tier 3  사용자 컨테이너 오케스트레이터 에이전트  (기존 per-user 워커가 돌리는 그 오케스트레이터)     │
│           │  배정 티켓 플랜 수립 → 레포의 ai-dlc 서브에이전트 호출 → 결과 수집·리뷰 → 위로 반환      │
│           ▼                                                                                        │
│ Tier 4  레포 ai-dlc 서브에이전트  (실제 코딩 워커)                                                  │
└────────────────────────────────────────────────────────────────────────────────────────────────┘
```

**소유 경계가 이 설계의 척추다.** 디스패처(하네스)는 Tier-1/2를 **새로** 도입하고 Tier-3를
띄우는 **실행 모드·세션 수명·전송로**만 바꾼다. **Tier-3의 오케스트레이터 룰북 동작과
Tier-4의 ai-dlc 서브에이전트는 프레임워크가 지금도 하는 일 그대로** — 이번 변경에서 **한 줄도
건드리지 않는다**(§3.0 불변식 참조).

- **Tier 1 — 중앙 오케스트레이터**: 스케줄링/조율만. 코드를 절대 편집하지 않는다. 레포락
  상태 + 실시간 자원 헤드룸을 읽어 무엇을/몇 개를/어떤 순서로 굴릴지 **동적** 결정.
  Tier-2를 온디맨드 spawn. **모든 일이 소진되면** wrap-up(예: Google Chat 알림) 후
  **종료** — 유휴 데몬을 남기지 않는다.
- **Tier 2 — 중앙 서브에이전트(사용자별/태스크별)**: 그 사용자/태스크의 티켓 배치를 받아
  순서·병렬성을 **레포락 상태를 참조해 스스로** 판단하고, **실제 작업은 소유 사용자
  컨테이너에 위임**하고 응답을 **기다렸다** 리뷰해 Tier-1에 보고. 배정 티켓 소진 시 종료.
- **Tier 3 — 사용자 컨테이너 오케스트레이터(진화형 워커)**: 배정 티켓을 받아 플랜 수립,
  레포의 **ai-dlc 서브에이전트**에게 실제 코딩을 위임, 결과를 모아 리뷰해 Tier-2 호출자에게
  반환. 배정 티켓 소진 시 종료.
- **Tier 4 — 레포 ai-dlc 서브에이전트**: 실제 코딩 워커(기존).

### 3.2 노드 생명주기 (모든 티어 공통 — Central 포함)

이것이 설계의 핵심 불변식이다:

1. **온디맨드 spawn** — 필요할 때만 뜬다.
2. **살아있는 노드에 티켓 추가 주입 가능** — 아직 pending/active 작업이 있는 노드에
   티켓을 **append**할 수 있다(사용자가 작업 도중 후속 지시를 보내는 것과 동일한
   follow-up injection). 노드는 이미 문맥을 가지고 있으므로 **직렬 vs 병렬을 스스로 판단**.
3. **큐 드레인 시 종료** — 배정 큐가 비면 노드는 **종료**한다(상시 데몬 아님).
4. **신규 티켓 도착 라우팅**: 그 스코프(사용자/태스크)의 **살아있는 노드(작업 중이든
   대기 중이든)가 있으면 → 그 노드에 hand-off/append**; 없으면 → **새 노드 spawn**.

### 3.3 핵심 enabler (구체화)

#### enabler 1 — 지속하며 await 가능한 세션 (HAN-537 정면 해결)

각 노드는 **살아있는 세션**으로 뜬다. 두 가지 실현 경로:

- **(a) Claude CLI 양방향 스트림**: `claude --input-format stream-json --output-format
  stream-json`(+ `--verbose`, `--dangerously-skip-permissions`). stdin으로 user 메시지를
  **JSON 라인**으로 밀어넣고 stdout에서 이벤트를 읽는다. 프로세스가 **살아있는 채로 여러
  턴**을 처리한다.
- **(b) Claude Agent SDK 세션**: 프로그램적 세션 객체로 메시지를 주고받는다(장수 프로세스
  안에서 세션을 보유).

**티켓 주입(HOW)**: 살아있는 세션의 stdin에 user 메시지 한 줄을 append한다 — 예:
`{"type":"user","message":{"role":"user","content":[{"type":"text","text":"<티켓
지시>"}]}}\n`. 이는 §3.2의 follow-up injection의 물리적 실현이다.

**완료 대기(HOW)**: 노드가 코딩을 백그라운드 서브에이전트에 위임하고 **턴을 종료해도**,
세션이 살아있으므로 서브에이전트 완료 알림이 **다음 턴으로 배달**되어 노드가 이어서 커밋한다.
**이것이 정확히 one-shot `claude -p`가 못 하던 것**이며 HAN-537의 근본 해결이다.

**임시성**: 세션은 지속하되 **영구는 아니다** — 배정 큐가 드레인되면 stdin을 닫고 프로세스를
정리해 종료한다(§3.2-3).

#### enabler 2 — 레포락은 결정적 메커니즘/공유 참조 상태로 유지

레포락(§1.2)을 **제거하지 않는다**. 상호배제는 **기계적·재시작 안전**으로 남는다. 바뀌는
것은 **정책의 소재**뿐: "레포 X 잠김 → 레포 Y 티켓을 골라라" 같은 판단을 에이전트가
레포락 상태를 **읽어서** 내린다. 즉 락은 mechanism, 선택은 policy(agent-driven).

- 구현: 스케줄러의 `_snapshot()`/`locked_repos`(`scheduler.py:469-494`)를 Tier-1/2가
  **읽기 전용으로 조회**할 수 있는 API로 노출. 점유(running 표시)는 여전히 스케줄러가
  결정적으로 수행.

#### enabler 3 — 임의 상한 없음, 실제 자원으로 경계 + 루프가드 대체

- 고정 `global=3`/`per_user=1`은 이미 없다(§1.6). 동시성은 **에이전트 판단**이되, 안전
  경계는 **컨테이너 단위 도커 자원 한도**(`spawner.py:31` `mem_limit` 등, 결정적·per-container)
  로 둔다 — LLM이 판단하는 전역 천장이 아니라 결정적 물리 한도.
- 서버 수준 어드미션(`scheduler.py:177-189`)은 2차 방어로 유지.
- **⚠️ 루프가드 필수**: 옛 `per_user_cap=1`이 겸하던 재귀-디스패치 방지가 사라진 자리에,
  현행은 dedup+워터마크(§2.3)로 버틴다. 그러나 **시스템/에이전트가 티켓을 생성**할 수 있는
  계층에서는 다음을 **반드시** 추가한다:
  - **티켓 provenance(출처 태깅)**: 잡에 `origin`(human | system | agent) +
    `parent_ticket` + `root_ticket`을 붙인다(Job 스키마 확장, `queue.py:109~`).
  - **depth limit**: `depth` 필드를 두고 시스템-생성 티켓이 만드는 하위 티켓의 depth를
    +1, 상한(예: 2~3) 초과 시 생성 거부 → **fork-bomb 차단**.
  - dedup 게이트(`gate.py`)는 그대로 1차 방어로 유지.

#### enabler 4 — 자격/귀속 격리 보존

실제 작업은 **각 사용자 본인 컨테이너**에서 그 사용자의 Jira/GitLab 토큰 + git author로
돈다(`build_env` `agent_runner.py:534-602`, 스포너의 per-user 시크릿 전달 —
지금은 마운트가 아니라 스폰 시 주입이다 `spawner.py`·`inject.py`). Central은 **스케줄링만** 한다. 이것이 per-user 컨테이너가 존재하는 이유이며
계층화에도 불변으로 유지된다. Tier-1/2(central)는 사용자 토큰을 만지지 않는다.

#### enabler 5 — 크로스-티어 트랜스포트: 단방향 큐 → 요청/응답(await)

현재는 **단방향 비동기**다: central→worker는 `GET /next`(폴), worker→central은 채널 F
`POST …/status`(단방향 회신) (`dispatch.py`). 목표는 Tier-2 호출자가 위임 결과를
**티켓 단위로 correlate해 await**할 수 있는 요청/응답이다.

- **설계**: `correlation_id = ticket`(+ attempt)로 요청↔응답을 맞춘다. Tier-2는 위임을
  보내고 해당 correlation의 응답이 올 때까지 논블로킹 대기(살아있는 세션이라 가능).
- **점진 이행**: 기존 채널 F를 폐기하지 않고, `status` 콜백에 `correlation_id`와 `terminal`
  플래그를 추가해 **응답 이벤트**로 승격. Tier-2는 이 콜백을 await 프리미티브로 소비한다.
  (완전한 양방향 소켓 대신, 폴/콜백 위에 correlation 레이어를 얹는 최소 변경.)

#### enabler 6 — 취소 세분화 (형제 작업 보호)

- **현행**: 취소는 control 채널 폴링(`GET …/control`) → 워커가 subprocess를
  **종료(kill)** + 롤백 후 cancelled 회신(`worker.py:_process_job`/`_handle_cancel`,
  `agent_runner.py:_consume`의 cancel 분기 `:740-751`). **현재는 잡=독립 subprocess**라
  한 잡 취소가 형제를 죽이지 않는다.
- **⚠️ 목표에서의 변화**: 여러 티켓이 **하나의 살아있는 세션**을 공유하면(§3.2), "프로세스를
  죽인다"는 형제 티켓까지 날린다. 따라서 취소는 **세션/프로세스 teardown이 아니라 특정
  위임 단위(delegated unit)를 겨냥**해야 한다:
  - 위임 단위마다 **cancel token/handle**을 부여(correlation_id 기반).
  - 취소 = 해당 서브에이전트/위임에 중단 신호 + 그 단위만 롤백; 세션은 살아남아 형제 계속.
  - §10 취소 모델을 "process kill" → "unit-scoped abort"로 재정의. terminal 회신도 잡
    단위(correlation) 유지.

#### enabler 7 — 병렬 작업 격리: git worktree

- 한 노드가 **같은 사용자의 여러 티켓을 병렬** 실행할 때, 병렬 단위마다 **git worktree
  격리**를 쓴다. 레포락이 **같은 레포**를 직렬화하고, **다른 레포**는 격리 워크트리에서
  병렬.
- 현행은 단일 공유 클론(`worker.py:478-484`)이라 같은 레포 병렬을 못 연다(§2.2). 워크트리
  도입 시 같은 레포라도 티켓별 워크트리로 병렬화 여지가 생긴다.
- **⚠️ 알려진 주의**: **같은 레포**에 대한 워크트리 격리는 조심하지 않으면 여전히
  **교차 오염**될 수 있다(공유 오브젝트 DB, 인덱스/락, 브랜치 충돌, 서브모듈, 빌드
  아티팩트 공유 등). 따라서 초기에는 **레포락으로 같은 레포는 직렬 유지**하고, 워크트리
  병렬은 다른 레포 우선 → 같은 레포 병렬은 격리 안전성 검증 후 단계적으로 연다. (오너 메모의
  "worktree isolation parallel agents" 교훈과 정합.)

- 검증: 같은 사용자·다른 레포 2티켓 동시 커밋, 교차 오염 0. depth 상한 초과 생성 거부.

### Phase 3b — 센트럴 오케스트레이터를 **repo-resolver-only → 조율 허브(Tier-1/2)** 로 확장

**목표**: §1.7의 센트럴 에이전트를 "티켓당 레포 판단" 한 가지 용처에서 **Tier-1 조율 허브 +
Tier-2 서브에이전트**로 키운다. 스케줄링/조율 **판단**(무엇을/언제/얼마나/어떤 순서)을
에이전트로 옮기되, **상호배제·자원 안전은 결정적 파이썬에 그대로 남긴다**(§3.0 불변식).

#### 3b.0 설계 결정 — 에이전트 판단 vs 파이썬 스케줄러의 권한 분할 (**본 Phase의 척추**)

이 문서에서 가장 중요한 한 줄: **"에이전트가 제안하고, 파이썬이 강제한다(agent proposes,
Python enforces)."**

- **파이썬(`RepoLockScheduler` + 자원 어드미션)이 유일 권한으로 유지하는 것**: 레포 단위
  **상호배제**(레포락 = 활성 잡의 순수 함수, `scheduler.py:496-521`)와 **자원 어드미션**
  (mem/load 헤드룸, `scheduler.py:177-197`). 결정적·재시작 안전·감사 가능. **LLM 경로에
  절대 넣지 않는다.**
- **에이전트(Tier-1/2)의 판단으로 옮기는 것**: 적격·admit 가능한 **집합 위에서의 정책** 뿐 —
  (a) **크로스-티켓 순서**(어느 티켓을 먼저), (b) **배치**(어떤 티켓들을 한 Tier-2 노드로
  묶을지), (c) **페이싱**(헤드룸을 얼마나 공격적으로 채울지). 에이전트는 레포락 스냅샷 +
  자원 헤드룸을 **읽기 전용으로 조회**(enabler 2, 3b.1)해 **디스패치 순서를 제안**한다.
- **에이전트는 판단하고 파이썬을 호출해 기록·강제한다(§5 D1 확정)**: 에이전트가 순서/배치/
  페이싱을 **결정**하면, 그 결정을 **파이썬 도구를 호출해 record**(target_repos·레포락 등)하고
  파이썬이 **강제**한다. 강제 지점은 그대로 `tick()` — 매 admit는 여전히 파이썬의 레포락 +
  어드미션 게이트를 통과해야 실행된다. 에이전트가 충돌하는 순서를 제안해도 파이썬이 그냥
  admit하지 않을 뿐 — **에이전트가 가드를 우회하지 못한다.** 모든 불변식(안전의 결정성·재시작
  안전·상호배제 무-LLM)이 보존된다.
- **에이전트는 스케줄링 결정 + 근거를 로그로 남긴다(§5 D1 확정)**: 비결정적 판단(§6)을 감사
  가능하게 하고, **이후 결정이 그 이력을 문맥으로 읽도록** 결정·근거를 명시 로그한다.

> ✅ 이 분할은 **오너 확정(§5 D1 = (a) 제안/강제 + 로깅)** 이다. (더 약한 "크로스-티켓 순서만",
> 더 강한 "에이전트 디스패치 주도"는 **기각**). **권한을 에이전트로 더 줄수록 적응성↑·
> 결정성/감사성↓** — (a)가 안전과 가치의 균형점이며, 로깅이 감사성 손실을 상쇄한다.

#### 3b 증분 단계 (각각 독립 배포 가능 — 3a처럼)

**Phase 3b-0 — 읽기 전용 상태 API (기반, 행동 변화 0).** 스케줄러의 `_snapshot()`/
`locked_repos` + 자원 프로브를 에이전트가 **읽기 전용**으로 조회하는 내부 API로 노출
(enabler 2). 점유(running 표시)는 여전히 파이썬이 결정적으로 수행. **단독 배포**: 접근자만
추가, 에이전트 없음 → 무위험. 검증: API가 라이브 락/헤드룸을 정확히 반영, 쓰기 경로 0.

**Phase 3b-1 — 채널 F에 명시적 id 요청/응답 레이어 (트랜스포트 기반, §5 D4 확정).** 채널 F
`status` 콜백(`dispatch.py:92-129`)에 `correlation_id`(= ticket+attempt) + `terminal`
플래그를 추가하고, 도착한 결과를 그 **명시적 id로 pending과 매칭**하는 **센트럴 측 pending
레지스트리**를 얹는다(enabler 5). **await/future가 아니라 id 매칭**이다 — id를 숨기지 않으므로
여러 동시 위임이 투명하게 멀티플렉싱되고, **pending은 영속 잡 상태에서 파생**돼 재시작 안전.
**하위호환**: 구 워커는 이 필드를 안 보내므로 기존 동작으로 폴백. **단독 배포**: 트랜스포트만
준비, 티어 에이전트 없음. 검증: 티켓 완료 회신이 정확한 pending을 id로 해소, 재시작 후
correlation 재구성(잡 상태 = 진실원).

**Phase 3b-2 — 단일 사용자용 Tier-2 서브에이전트 (위임 단위의 최소 착지).** **한 종류의
Tier-2 노드**를 도입: 한 사용자의 티켓 배치를 받아 3b-0 상태를 조회해 순서를 **제안**하고,
각 티켓을 **그 사용자 본인의 Tier-3 컨테이너**(기존 디스패치 경로)에 위임하고, 3b-1
correlation으로 **await**하고, 완료 회신의 `cycle_log_path`(§1.5)를 읽어 **리뷰**한 뒤
Tier-1(또는 초기엔 로그)에 **보고**한다. 큐 드레인 시 **종료**. 파이썬 스케줄러가 admit
가드로 그대로(3b.0). **피처 플래그 opt-in**: 파일럿 사용자 1명만 이 경로로, 나머지는 순수
파이썬 디스패치 유지 → "제안/강제" 모델의 첫 실증. 검증: 파일럿 사용자 티켓들이 에이전트
순서 제안 + 파이썬 가드로 정상 완료; 비파일럿 경로 회귀 0.

**Phase 3b-3 — Tier-1 허브 + 노드 생명주기/라우팅.** Tier-1 도입: enqueue 시 3b-0 헤드룸을
조회해 **어떤 Tier-2 스코프를 spawn / 어느 살아있는 노드에 주입**할지 결정(§3.2 라우팅) —
살아있는 노드 있으면 append, 없으면 spawn. 드레인 → wrap-up(예: Google Chat 알림) → **종료**
(유휴 데몬 0). 살아있는 노드 재사용을 위한 **노드 레지스트리**. **3b-2 실증 후 배포**: Tier-1이
복수 Tier-2를 조율. 검증: 살아있는 노드에 후속 티켓 append가 재spawn 없이 흡수; 전 작업
드레인 시 모든 티어 종료.

**Phase 3b-4 — 취소 세분화 + 주입 하드닝.** correlation 기반 **unit-scoped abort**(enabler 6):
한 티켓 취소가 공유 노드/형제 티켓을 안 죽인다. 살아있는 노드 stdin append로 티켓 주입
(§3.2-2, `_encode_user_message` 재사용). **조율 완결 단계로 배포**. 검증: 한 티켓 취소가
형제 무영향; 라이브 노드 주입이 문맥 유지.

> **각 단계 독립성**: 3b-0/3b-1은 **행동 변화 0의 순수 기반**(먼저·안전하게 배포), 3b-2는
> **피처 플래그 opt-in**(파일럿 1명), 3b-3/3b-4는 그 위에 조율·취소를 얹는다 — 3a가 그랬듯
> 각 단계가 단독으로 가치·롤백 가능.

#### 3b 전송/자원 상세 (설계 포인트, 포크는 §5)

- **트랜스포트(enabler 5, §5 D4 확정 = 명시적 id 요청/응답 over 채널 F)**: 이행은 **폴+콜백 위
  명시적 id correlation 레이어**(3b-1). Tier-1/2가 **센트럴 파이썬 안**(Agent SDK, D3)이어도,
  실제 작업은 **별도 사용자 컨테이너의 Tier-3**(subprocess-claude)가 하므로 결과는 채널 F로
  돌아온다 — 따라서 **인프로세스 future는 쓰지 않는다**(id를 숨겨 멀티플렉싱 불투명 + Tier-3가
  별도 프로세스라 애초에 불가). 각 위임은 **명시적 티켓/correlation id**를 실어 보내고, 컨테이너가
  그 id로 태깅해 채널 F POST → 센트럴이 id로 pending과 매칭한다. pending은 **영속 잡 상태에서
  파생**되어 재시작 안전. 새 네트워크 홉 0(센트럴이 이미 채널 F POST 수신).
- **자격 격리 불변(enabler 4)**: 실제 작업은 여전히 **각 사용자 컨테이너**에서 그 사용자
  토큰·git author로 돈다. Tier-1/2(센트럴)는 **스케줄링/조율만**, 사용자 자격을 만지지 않는다.
  → Tier-2의 위임 대상은 항상 소유 사용자 컨테이너다(이게 §5 D2 "per-user vs per-task"에 영향).
- **센트럴 에이전트 자원 경계(포크 §5 D5)**: 지속 Tier-1이 busy-loop로 추론하면 센트럴 자기
  토큰(축1, `repo_resolver`만 쓰던 쿨다운)이 급증한다. **이벤트 구동 Tier-1**(enqueue/terminal
  에만 깨어남) 권장. 센트럴 컨테이너엔 워커 같은 `mem_limit`(§1.5 `spawner.py:31`)가 없다 —
  Tier-1/2 자체 풋프린트 상한도 정해야 한다.

## 5. 오너가 정해야 할 열린 결정 (Open Decisions) — **Phase 3b 착수 전 결정 필요**

아래는 추측으로 메울 수 없는 **설계 포크**였다. 각 항목은 구체 옵션 + 트레이드오프를 달았고,
Phase 3b 본문(§4)이 `D#`로 참조한다. **D1–D4는 오너 확정(DECIDED) — 아래 표기대로 Phase 3b
착수 기준이다.** D5–D9는 여전히 열린 결정(구현 시점에 확정).

**D1 — 스케줄링 권한 분할(에이전트 vs 파이썬). ✅ DECIDED = (a) 에이전트 제안 / 파이썬 강제 +
로깅.** *가장 중요.*
- **확정**: 센트럴 에이전트가 순서/배치/페이싱을 **판단**하고, **파이썬을 호출**해 그 결정을
  **기록(record)하고 강제(enforce)** 한다 — 레포락·어드미션은 파이썬이 유일 권한으로 유지.
  에이전트는 자신의 스케줄링 결정 + **근거(rationale)를 로그로 남겨**, 이후 결정이 그 문맥을
  읽을 수 있게 한다(결정 이력 = 다음 판단의 입력).
- (a) **에이전트 제안 / 파이썬 강제**(✅ **채택**, 3b.0 기본) — 에이전트는 적격 집합의 순서·
  배치·페이싱만, 상호배제·어드미션은 파이썬 `tick()`이 강제. 결정성·감사성 최대 보존.
- (b) 에이전트=크로스티켓 순서만, 파이썬이 나머지 전부 — 가장 보수적, 에이전트 가치 최소. *기각.*
- (c) 에이전트가 디스패치 주도, 파이썬은 순수 가드 — 가장 적응적, 결정성/재현성↓·감사 난도↑. *기각.*
- 트레이드오프: **에이전트 권한↑ = 적응성↑·결정성/감사성↓.** (a)가 안전과 가치의 균형점.
- **로깅 근거**: 에이전트가 "제안"만 하고 파이썬이 강제하므로, 결정의 **비결정성**(§6 리스크)을
  감사 가능하게 만들려면 결정+근거의 명시 로그가 필수 — 재현·디버그·후속 판단의 문맥원이 된다.

**D2 — Tier-2 분할 축. ✅ DECIDED = per-user Tier-2 (드레인 시 에이전트 프로세스만 종료).**
- **확정 (분할 축)**: **per-user**. 한 Tier-2 ↔ 한 사용자 컨테이너 ↔ 그 사용자 티켓 배치 —
  enabler 4(자격 격리)의 컨테이너 경계와 자연 정합, 위임 팬아웃 단순.
- **확정 (드레인 생명주기)**: 큐 드레인 시 종료하는 것은 **claude 에이전트 프로세스**(사용자
  컨테이너의 오케스트레이터 에이전트)뿐이며, **컨테이너는 종료하지 않는다** — 컨테이너는
  장수(long-lived) 인프라다. 에이전트는 **일이 있는 동안 지속**(센트럴처럼 후속 티켓을 계속
  수신)하고 **드레인 시 종료**하는 persistent-but-ephemeral 노드다. **모든 티어가 같은
  생명주기**: 에이전트=임시(드레인 시 종료), 컨테이너/인프라=지속(§3.2와 정합).
- per-task/에픽: 크로스-티켓 순서 일관성↑이나 여러 컨테이너 팬아웃 → 자격 격리와 마찰. *기각*
  (순서 일관성이 실측 병목일 때만 재검토).

**D3 — Tier-1/2 실체(embodiment). ✅ DECIDED = (a) Agent SDK 인프로세스(센트럴 파이썬 안).**
- **확정**: Tier-1·Tier-2는 센트럴 파이썬 안의 **인프로세스 Agent SDK 서브에이전트**로 돈다.
- **커스텀 파이썬 도구는 오직 리소스 조작(resource ops) 전용** — 스케줄러 상태 읽기(3b-0),
  target_repos/레포락 기록(record), 사용자 컨테이너로 디스패치, 결과 fetch. **그 외 없음.**
- **서브에이전트 spawn은 에이전트의 네이티브 능력(Agent/Task)** 이지 파이썬 도구가 아니다 —
  Tier-1이 Tier-2를 띄우는 것은 SDK 고유 기능으로 한다(파이썬 spawn 도구를 만들지 않는다).
- **Tier-3(사용자 컨테이너 오케스트레이터)는 그대로 워커 안의 별도 subprocess-claude**로 남는다
  (Phase-1 메커니즘). Tier-2→Tier-3 경계는 인프로세스가 아니라 **트랜스포트(D4)** 다 — 결과가
  사용자 컨테이너에서 채널 F로 돌아오므로 인프로세스 future로는 성립하지 않는다.
- (b) `claude --input-format stream-json` 서브프로세스 브리지 — 브리지 왕복 비용. *기각.*

**D4 — 요청/응답 트랜스포트 형태(enabler 5). ✅ DECIDED = (a) 명시적 id 요청/응답 over 채널 F
(폴+콜백). NOT await/future, NOT SSE.**
- **확정**: 각 사용자 컨테이너로의 위임은 **명시적 티켓/correlation id**(= 기존 티켓/잡 id)를
  실어 보낸다. 컨테이너는 결과를 **그 id로 태깅**해 기존 티켓-키드 채널 F(`POST …/status`)로
  POST하고, 센트럴은 도착한 결과를 **id로 pending과 매칭**한다. 에이전트는 id를 **명시적으로
  본다** → 여러 동시 위임 사이의 **투명한 멀티플렉싱**(어느 결과가 어느 위임인지 id로 구분).
  pending은 **영속 잡 상태에서 파생**되므로 **재시작 안전**하다.
- (a) **폴+콜백 위 명시적 id correlation 레이어**(✅ **채택**, 3b-1) — 재시작 안전, 지연은
  허용 가능. 채널 F가 이미 존재하므로 새 네트워크 홉 0.
- (b) ② **SSE/롱폴** — *기각*: 대기 연결 유지 비용 + **재시작 취약**(연결 상태가 진실원이 되면
  센트럴 재배포 시 유실).
- (c) ③ **인프로세스 await/future**(D3-a와 결합) — *기각*: future 객체가 **id를 숨겨**, 여러
  동시 위임 시 **어느 응답이 어느 위임인지 모호**(멀티플렉싱 불투명). 또한 Tier-3가 별도 컨테이너
  프로세스(D3)라 결과가 채널 F로 넘어와야 하므로 인프로세스 future로는 애초에 성립 불가.
- **D3과의 관계 갱신**: 이전 초안은 "D3-a면 D4-c(인프로세스 future)가 최적"이라 커플링했으나,
  Tier-3가 별도 컨테이너에 남는 이상(D3) 결과 경로는 반드시 채널 F다 → **D3-a여도 D4는 (a)**.

**D5 — 센트럴 에이전트 자원 경계.**
- 지속 Tier-1을 **이벤트 구동**(enqueue/terminal에만 깨어남, 권장) vs **주기적 추론 루프**?
  전자는 축1 토큰 소모·유휴 비용 최소.
- 센트럴 컨테이너엔 워커 같은 `mem_limit`가 없다(§1.5) — Tier-1/2 자체 풋프린트 상한을
  어디에 두나(센트럴 컨테이너 mem_limit? Tier-2 노드 수 상한?).
- 축1 토큰 쿨다운(`repo_resolver` 전용이던 것)이 **스케줄링 에이전트에도 적용**되나? 조율이
  토큰 한도로 멎으면 디스패치 전체가 정지 — 리졸버와 다른 폴백(파이썬 순수 디스패치로 저하)
  이 필요.

**D6 — Tier-1 자체가 파이썬 스케줄러를 대체(supersede)하나, 위에 얹히나?**
- (권장) `RepoLockScheduler.tick()`을 **실행자로 유지**, Tier-1은 적격 큐를 재정렬/배치만.
- (대안) Tier-1이 실행자가 되어 enqueue/dispatch를 직접 호출 — D1-c와 동류, 재시작 안전성
  재설계 필요. **권장하지 않음**(현행 재시작 불변식을 깬다).

**D7 — 살아있는 티어 세션의 크래시/재배포 복원.**
- 티켓 큐(jobs.json)는 이미 재시작 안전(§1.2). 그러나 **Tier-1/2 세션 문맥**은?
  `--resume`(티켓 uuid5)로 티어 세션까지 복원 vs 큐만 복원하고 세션은 새로 시작(문맥 유실
  허용)? 후자가 단순하고 큐가 진실원이라 대개 충분 — **결정 필요**.

**D8 — wrap-up/드레인 종료의 원자성 + 콜드스타트.**
- "모든 일 드레인"을 신규 도착과 경합 없이 **원자적으로** 판정하는 법? 종료 직후 신규 티켓 →
  재spawn 지연(콜드스타트) 비용? **keep-alive 유예창**(드레인 후 N초 대기 후 종료)을 둘까?

**D9(부차) — 같은 레포 워크트리 병렬의 안전 한계(Phase 2, enabler 7).** 어디까지 안전한가
(빌드 캐시/인덱스/서브모듈)? 같은 레포 병렬을 아예 금지(레포락 유지)가 단순·안전하지 않나?
(오너 메모 "worktree isolation parallel agents" 교훈과 정합 — 초기 금지 권장.)

## 6. 리스크 (정직하게)

- **LLM 판단의 비결정성**: 스케줄링을 에이전트로 옮기면 재현성·감사성이 낮아진다. 완화 —
  상호배제는 결정적 레포락 유지(enabler 2), 안전 경계는 결정적 자원/컨테이너 한도(enabler 3),
  에이전트는 **선택**만.
- **살아있는 세션의 비용/누수**: 지속 세션은 프로세스·토큰·메모리를 붙든다. 드레인-종료
  규율(§3.2-3)이 안 지켜지면 유휴 데몬·토큰 낭비. 완화 — 명시적 종료 조건 + 하트비트/타임아웃.
- **취소 세분화 미스**: 세션 공유 상태에서 unit-scoped abort가 새면 형제 오염/데이터
  경합. 완화 — 병렬 단위 = 워크트리 격리 + correlation별 cancel handle, 초기엔 같은 레포
  직렬.
- **워크트리 교차 오염**: enabler 7의 알려진 함정 — 같은 레포 워크트리 병렬은 신중히. 완화 —
  단계적 개방, 우선 다른 레포만.
- **fork-bomb**: provenance/depth 가드(enabler 3)가 없으면 시스템-생성 티켓이 폭주. 완화 —
  depth 상한 + origin 태깅을 Phase 2에서 선제 도입.
- **트랜스포트 복잡도**: 단방향→요청/응답 전환이 재시작 안전성/멱등성을 깨기 쉽다. 완화 —
  correlation=티켓 기반 멱등, 채널 F 위 최소 증분(enabler 5).
- **범위 크리프**: 4-티어를 한 번에 지으려다 각 단계 배포가 늦어짐. 완화 — Phase 1(지속
  세션)·3a(dlc-meta)는 이미 착지; Phase 3b는 **3b-0/3b-1(행동 변화 0 기반) → 3b-2(피처
  플래그 파일럿 1명) → 3b-3/3b-4**로 쪼개 각 단계 단독 배포·롤백.

## 0. 요약 (TL;DR)

같은 **ai-dlc-orchestrator 에이전트**가 3층으로 프랙탈하게 동작한다. 계층 구분은 “다른 프로그램”이 아니라 **누가 이벤트를 넣어주느냐**의 차이뿐이다.

- **센트럴 에이전트**(세션) ← Jira 이벤트. 레포락을 존중해 판단하고, **사용자별 서브에이전트**를 네이티브로 스폰(또는 이미 돌고 있으면 이어위임).
- **사용자별 서브에이전트**(센트럴 컨테이너 내, 네이티브 서브) → `docker exec` 로 해당 **사용자 컨테이너의 ai-dlc-orchestrator 에이전트**(세션)를 구동/이어주입.
- **사용자 컨테이너 에이전트**(세션) → **레포별 서브에이전트**를 네이티브로 스폰해 실제 작업.

**동작의 틀은 코드가 아니라 프롬프트로 잡는다.** 각 계층은 “operating frame”(역할+행동 규약) 프롬프트를 데이터(txt/py 상수)로 보관하고, 파이썬이 세션 구동 시 주입한다. 완료는 **파이썬이 stream 파싱해서 잡는 게 아니라 상위 에이전트가 하위의 리치 완료-리포트를 관찰/수신해서** 잡는다(= GitLab CI 완료를 관찰하듯). 파이썬은 최소 기계장치(컨테이너 수명·세션 주입핸들·레포락 가드·gchat 송신 py)만 남는다.

## 1. 핵심 원칙 (Invariants)

1. **프랙탈 동일-에이전트.** 센트럴·각 사용자 컨테이너에 들어가는 것은 전부 동일한 ai-dlc-orchestrator 에이전트다. `너 = 센트럴 에이전트 = 사용자 컨테이너 에이전트`.
2. **세션은 컨테이너 경계 때문에만 생긴다.** 한 컨테이너 안에서 하위를 부르는 것은 전부 네이티브 서브에이전트 호출(세션 아님). “세션”이란 곧 “그 컨테이너에 사는 에이전트 프로세스”이며, 다른 컨테이너에 에이전트를 두려면 그 안에 claude를 하나 띄워야 하기에 생긴다.
3. **틀은 프롬프트로.** 지능·판단·완료리포트 작성은 에이전트가. 강제·격리·수명·좀비방지 같은 기계적 보장만 파이썬/OS가.
4. **완료는 관찰(observe)로 전파.** 하위가 리치 완료-리포트를 방출하고, 상위가 그것을 수신·판단해 위로 올린다. 바 마커/불리언이 아니라 **내용(무슨 작업·레포·MR·테스트·사이클로그)** 을 실어 올린다.
5. **레포락 스케줄러는 가드레일로 유지.** 에이전트가 제안(target_repos·순서), 파이썬 `RepoLockScheduler` 가 상호배제를 강제(“agent proposes / Python enforces”). 선행 문서 §1.2 그대로.
6. **프레임워크 불가침.** `ai-dlc-orchestrator` 리포는 손대지 않는다(하니스/파이썬만). gitlab-origin 이 정본 원격.

## 2. 프랙탈 위임 트리

```
Jira 이벤트
  └▶ 센트럴 에이전트 (세션; 센트럴 컨테이너)
        ├▶ 사용자별 서브에이전트 (네이티브 서브; 센트럴 컨테이너 내)
        │     └──docker exec──▶ 사용자 컨테이너 에이전트 (세션; jad-worker-<user>)
        │                           └▶ 레포별 서브에이전트 (네이티브 서브) → 실제 코드작업
        │                           ▲ (레포 서브들 리치 요약 반환 → aggregate)
        │     ▲ 사용자 컨테이너 에이전트가 "티켓 리치 완료-리포트" 방출 → 사용자별 서브가 관찰/수신
        │     └ 판단: 추가작업 필요 → 이어서 지시 / 진짜 끝 → 완료-리포트 상신
        └▶ (티켓 완료-리포트 수신) → `python gchat.py <report>` 호출 → 구글챗 래핑·송신
```

**소유 경계**
- 사용자 간 병렬성 = 사용자별 서브에이전트가 병렬로 존재(사용자당 하나).
- 사용자 내 작업 = 사용자 컨테이너 에이전트 하나가 티켓들을 순차 턴으로 받되, 필요 시 자기 레포별 서브로 팬아웃.
- 커밋/MR 신원·자원 격리 = 사용자 컨테이너 단위(그래서 컨테이너를 유지 = 결정 A).

## 3. 계층별 Operating Frame (프롬프트 = 데이터, 파이썬이 주입)

각 프레임은 외부 파일/상수로 보관하고 세션/서브 구동 시 핵심 지시 앞뒤에 주입한다. **살(intent framing)** 은 아래 규약을 포함한다.

### 3.1 센트럴 에이전트 프레임
- Jira 이벤트(신규/갱신 티켓) 수신.
- 레포락 상태를 존중해 무엇을·누구에게 보낼지 판단(제안). 파이썬 스케줄러가 상호배제 강제.
- 사용자별 서브에이전트 스폰; **해당 사용자 서브가 이미 돌고 있으면 새로 스폰하지 말고 그 서브에 이어위임.**
- **각 티켓 완료-리포트를 수신하면 `python gchat.py` (메시지 래퍼+송신 도구)를 호출하고 받은 완료 메시지를 인자로 전달**(래핑·송신).
- 모든 사용자별 서브가 작업을 마치고 사라지면 종료.

### 3.2 사용자별 서브에이전트 프레임 (센트럴 측)
- 담당 사용자의 티켓을 사용자 컨테이너 에이전트에 위임:
  - **이미 세션이 떠있으면 새로 띄우지 말고 그 세션에 추가 작업을 이어서 지시.** 없으면 기동.
  - 구동 시 컨테이너 에이전트 프레임(§3.3)을 함께 주입.
- 컨테이너 에이전트의 **리치 완료-리포트를 관찰/수신**.
- 판단(너처럼): 추가 작업 필요 → 컨테이너 에이전트에 이어서 지시 / 진짜 완료 → 완료-리포트를 센트럴에 상신.
- 담당 사용자의 모든 작업이 마무리되면(= 컨테이너 에이전트 종료 시점) 종료.

### 3.3 사용자 컨테이너 에이전트 프레임
- 위임된 티켓 수신 → 레포별 서브에이전트 스폰해 실제 작업.
- **모든 할당 작업이 끝나면 세션이 종료되게** 동작. 작업 중 추가 티켓이 주입되면 **이어서** 처리(내가 작업 중 추가 메시지 받듯).
- 티켓이 마무리되면 **무슨 작업·어느 레포·MR 링크·테스트 결과·사이클로그를 담은 리치 완료-리포트를 위로 방출.**
- 종료 시 **하위 좀비 없게 정리**(프롬프트 보조 + OS 백스톱 tini/killpg가 실보장).

### 3.4 레포별 서브에이전트 프레임 (leaf)
- 지정 레포에서 티켓 작업 수행(코드·테스트·MR).
- **리치 요약 반환**(변경점·MR·테스트). 상위가 이를 aggregate.

## 4. 노드 생명주기 (프랙탈 공통, drain-terminate)

- **사용자 컨테이너 에이전트** = 자기 할당 작업 전부 drain 시 종료. 유휴 = 프로세스 없음(정상).
- **센트럴 사용자별 서브** = 그 사용자 작업 drain 시(= 컨테이너 에이전트 종료) 종료.
- **센트럴 에이전트** = 모든 사용자별 서브 소멸 시 종료.
- 온디맨드 기동, 지속-while-work(작업 중엔 프로세스 유지), 재사용-if-up(이어주입), drain-종료. 컨테이너(`jad-worker-<user>`)는 `unless-stopped` 로 상시(선행 §1.5), 에이전트 프로세스만 수명제.

## 5. 완료 전파 (관찰형)

- **감지 방식**: 파이썬 `_consume` 의 stream-json `result` 파싱이 아니라, **상위 에이전트가 하위의 완료-리포트를 관찰/수신**. GitLab CI 완료를 폴/관찰하는 것과 동형.
- **신호의 내용**: 바 마커가 아니라 **에이전트가 쓴 리치 완료-리포트**(그래서 gchat 메시지 품질 = 에이전트 리포트 품질, 파이썬 템플릿 아님).
- **stdout 처리**: 세션 stdout는 로그파일로 흘려보내 파이프 데드락만 방지(라이브 파싱 리더 루프 불필요).
- **좀비**: 근본은 OS 리핑 문제 → **tini(PID1 리퍼) + killpg 프로세스그룹 종료**(선행 Phase 1 착지분)로 기계적 보장. 프롬프트 “정리하고 종료” 는 보조.

## 6. 파이썬으로 남는 최소 기계장치

1. **컨테이너 기동/종료** — `app/spawner.py` `ensure_worker`(컨테이너 재사용 게이트 이미 존재).
2. **세션 주입핸들** — 사용자 컨테이너의 지속 세션에 다음 티켓을 넣는 얇은 경로(stdout→로그, stdin 주입). 프로브가 **라이브 stdin 지속 주입**을 증명(§7). 대안 `--resume` 교차-exec 은 구현 시 실측 후 최단순 택1.
3. **레포락 가드** — `app/scheduler.py` `RepoLockScheduler` 그대로(상호배제 강제).
4. **gchat 송신 py** — 완료-리포트를 받아 구글챗 메시지로 래핑·송신(현 `app/notify.py` 재사용/추출).
5. **프롬프트 데이터** — 계층별 operating frame 을 외부 txt/py 로 보관, 주입.

## 7. 실측 검증 (프로덕션 이미지, 2026-08-20)

`jad-worker-yhchoi` 안에서 실제 dispatcher 프레이밍(`build_command` 지속형 + `_encode_user_message`)으로 프로브. `claude 2.1.237`.

- **한 세션 다중 순차 주입 PASS** — pid 고정, `--resume` 없이 라이브 stdin 으로 2차 티켓 처리.
- **헤드리스 서브에이전트 스폰 PASS** — 세션이 general-purpose 서브 스폰, 완료가 부모 턴으로 복귀, 서브 drain 후 최종 `result`.
- **완료 상관** — 주입 1건 = `result` 1건(고유 uuid). 필요 시 티켓 마커를 프롬프트에 심어 하드 상관 가능.
- **주의(참고)**: 이 CLI는 서브를 `background_tasks_changed` 가 아니라 `task_started/progress/updated/notification`(안정적 `task_id`) 로 흘린다. 단, 포그라운드 서브를 쓰는 본 모델에선 `result`=완료가 이미 정확해 **드레인/pending_bg 로직은 불필요(은퇴)**.

## 8. 은퇴/기각 (선행 3b 잔재)

- `app/agent_runner.py` `_consume` 의 **티켓당 소유→프로세스 kill** 모델, `pending_bg`/`_bg_pending_from_event` 드레인 게이팅 → **은퇴**(관찰형 완료로 대체).
- 3b-1 `app/pending.py` `PendingRegistry` / 명시적-id 전송로 → **사족**(에이전트 네이티브 상관으로 대체). 제거 대상.
- 3b-2 `app/tier2.py` 러너 스캐폴드(`MockTier2Runner`/`SdkTier2Runner`/`CliTier2Runner` 개념) 및 `app/tier2_tools.py` HTTP 자원툴, `/scheduler/state` 앞단 dispatch/poll 엔드포인트 구상 → **기각**(프롬프트-구동 관찰형이 대체). `state_snapshot`/`/scheduler/state` 는 진단용으로만 존치 가능.
- 선행 D3(in-process Agent SDK) 및 `claude-agent-sdk` 의존성 → **기각**(베이스가 이미 claude CLI; 네이티브 서브로 충분).

## 9. 빌드 페이징 + 컷오버 체크포인트

- **P1 — 컨테이너/워커 계층**: 컨테이너 에이전트·레포서브 프레임(데이터화), 사용자당 지속 세션 + 재사용-if-up 주입 게이트 + drain-종료, 리치 완료-리포트 방출. 기존 per-ticket kill 경로는 **비파괴적**으로 병행(플래그/신경로) 후 검증.
- **P2 — 센트럴 계층**: 센트럴 operating frame(데이터화)으로 센트럴을 지속 세션화(현 one-shot repo_resolver 흡수), 사용자별 서브 프레임, gchat.py 배선.
- **P3 — 정리**: §8 은퇴분 제거.
- **컷오버**: 프로덕션 실행핵(HAN-433 로 증명된 경로) 교체이므로, **실티켓이 새 경로로 통과하는 라이브 검증은 오너가 지켜볼 수 있는 시점에** 수행. 그 전까진 CI-green + 인컨테이너 프로브 e2e 로만 게이트.
